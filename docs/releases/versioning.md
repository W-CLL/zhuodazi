# 版本命名与发布规则

用户版本采用 `v主版本.功能版本.修复版本`（vX.x.xx），三个位置均为整数，不强制补零。安装包元数据省略 `v` 前缀。

| 变化 | 递增方式 | 示例 |
| --- | --- | --- |
| 修复缺陷、微调文案或既有交互 | 末位加 1 | v1.4.0 → v1.4.1 |
| 新增用户功能 | 中间位加 1，末位归零 | v1.3.11 → v1.4.0 |
| 大版本升级或重大不兼容变化 | 首位加 1，其余归零 | v1.4.2 → v2.0.0 |

Windows、macOS 和 Android 各自沿用已有版本序列。相同功能同时上线不意味着必须把 Android 跳到桌面端版本。本轮目标版本为 Windows / macOS v3.4.1、Android v1.5.1：修复体验到期后的设备活跃统计，并补充三端运行心跳，使用补丁版本。

版本基线以最后正式发布为准；同一未发布版本在验收中修复缺陷，不再额外增加用户版本。本轮对应用户更新说明为 `desktop-3.4.1.md` 和 `android-1.5.1.md`；版本文件与说明不代表安装包已经公开发布，发布状态以各渠道实际结果为准。

Android 的 `versionCode` 为独立、持续递增的安装编号，本轮为 25，用户版本为 v1.5.1，对应 Flutter 版本 `1.5.1+25`。交付已使用安装编号之外的新版本时递增；同一发布候选的测试、重新构建和转为正式发布沿用其版本与安装编号。覆盖安装必须同时满足相同包名、相同签名；远程稳定签名包与本地 Debug 应用分开。Debug 使用独立包名和 `-debug` 后缀，不覆盖正式应用。

Android 版本源为 `android/app/build.gradle.kts`；`mobile_ui/pubspec.yaml` 的版本与构建号必须同步。`scripts/check-release-consistency.py` 检查两者及对应更新说明，CI 在打包前执行。更新说明按平台和用户版本命名，使用用户能看懂的变化描述。

已有正式 Release 不得原地覆盖。版本比较使用三个整数逐位比较，不能使用字符串排序。发布前需要核对线上最新正式版本；正式发布时需同步 GitHub、后台更新清单和官网公开下载。
