## 1. 用户原始诉求与范围

1. 卸载桌搭子时，可以选择理由或直接卸载；后台记录已卸载，重新安装使用后再恢复状态。
2. 优化桌宠的词库导入，可以多选。用户已确认：既要一次导入多个文件，也要同时勾选多个词库使用。
3. 在桌搭子内浏览线上桌宠，点击预览；只开放后台选定的几个，或前五个供预览。用户已确认：预览限制作用于每个资源包内部的部分内容。用户付款时填写唯一标识备注，由已有微信机器人识别支付信息，关联账号与桌宠，再直接提供下载。产品形态接近扩展资源市场。

2026-10-28 补充确认：一个收费商品是同一角色的资源包，包含 25+ 动作或表情素材；普通款 2.8 元，复杂或热门款 5.8 元。采用微信收款码，先点击下单生成订单与尽量简单的短码，再弹出付款窗口；15 分钟内未支付则取消订单并关闭付款窗口。用户指定 wxlocal 作为待接入项目，源码核查见 5.5。

2026-10-28 本地调试补充确认：先做 Windows 版本，使用用户生成的 0.01 元收款码进行本地联调，不更新线上。付款备注码固定为三个数字加两个英文字母，例如 `123AB`，不区分大小写；编码容量、历史不复用和耗尽处理见 5.4。

2026-10-28 个人转账补充确认（以本条最新决定为准）：用户实测收款码连续备注会触发“频繁”提示，要求保留收款码并增加个人对个人转账。用户进一步明确“转了账就算直接成功，可以直接下放安装”：仅 `personal_transfer / incoming / observed / verified:false` 结构化转账事件在当前收款账号、本次五位备注码、金额、币种、稳定交易标识和有效时间严格匹配后，自动确认订单并开放下载权益，不等待微信领取或本地人工确认。`pay_subtype` 不用于推断到账；原事件仍为 `observed / verified:false`，订单成功是本地业务规则。普通收款码人工核对流程保留；本地商品仍是测试 ZIP，正式资源安装另属完整市场实现。

联合目标：用户从发现桌宠、试看、购买、下载到使用形成完整流程；后台能管理商品、处理到账和了解明确报告的卸载情况。

首版建议定位为“桌宠资源市场”：销售桌宠 / 桌宠资源包，下载后在现有桌宠功能中使用。可执行代码插件、第三方开发者入驻和交易分成留作后续方向，不作为本轮默认范围。

## 3. 需求 A：卸载反馈与安装状态

### 3.1 用户流程

1. 用户通过系统卸载桌搭子，出现正常卸载确认。
2. 提供可选原因，例如“不常用”“占用资源”“体验问题”“暂时不用”“其他”；其他说明可不填。
3. 同一处提供“确认卸载”和“跳过反馈并卸载”，不强制选择理由，不用多轮挽留阻止卸载。
4. 用户取消时，不标记已卸载。开始卸载也不能提前当作卸载成功。
5. 能确认卸载完成的客户端卸载流程，尽力发送完成报告和可选原因。网络错误不阻止或拖延卸载，采用有限等待。
6. 服务端收到可信完成报告后，保存设备、平台、版本、完成时间与原因，后台显示“已报告卸载”。
7. 用户重新安装并成功联网启动后，记录恢复时间，更新为“已安装”。仅重新下载安装包不触发恢复。

### 3.2 状态与规则

| 情况 | 后台处理 |
| --- | --- |
| 已收到卸载完成报告 | 安装状态保持“已报告卸载”，同时保留此前活跃历史 |
| 仅收到卸载开始 / 尝试报告 | 可保留过程记录，不标记完成 |
| 离线卸载、直接删除应用、无法发送完成报告 | 不臆测卸载；继续显示最后活跃时间与安装状态未知 |
| 用户退出、关机、休眠或断网 | 只更新或推导活跃状态，不标记卸载 |
| 收到同一次卸载的重复报告 | 幂等处理，不重复计数 |
| 卸载后有旧请求或旧进程心跳迟到 | 不清除卸载状态；恢复必须关联新的安装批次及其启动 |
| 重装后新安装批次启动成功 | 恢复为已安装，保留原卸载历史和原因 |
| 重装后旧卸载报告迟到 | 不覆盖新安装批次的状态 |
| 覆盖升级或安装器内部替换文件 | 不计为真实用户卸载 |

安装状态、活跃状态、设备授权、桌宠购买权益是四个不同维度。卸载不删除账号购买记录，也不直接撤销付费权益。设备授权额度是否自动释放需要另定规则，不能因为不活跃而自动解绑。

### 3.3 平台边界

- Windows：有现成卸载器，适合先实现完整流程；需核实卸载完成阶段如何发送报告，以及重新安装批次如何识别。
- macOS：直接拖入废纸篓不保证应用收到可靠通知。应用内自愿反馈入口可另行设计，不能把它宣传成所有卸载都会检测到。
- Android：系统卸载时不能依赖应用自身可靠执行卸载回调；不能承诺出现自定义理由页或必达报告。当前卸载会清除本地身份，重装可能成为新设备，应通过稳定账号恢复购买权益。
- Windows 的 AppData、macOS 的钥匙串通常会保留身份；此类保留数据与新安装批次要区分，避免误把重装当作普通启动或新购买用户。

### 3.4 验收要点

- 选理由、跳过、取消、完成、失败和离线流程均不混淆；反馈失败不妨碍卸载。
- 后台可查看卸载原因、时间、版本，并筛选已报告卸载设备。
- 普通退出、升级、迟到心跳不产生错误卸载或错误恢复。
- 重复上报不会重复统计，重装启动能恢复状态，历史保留。
- 卸载整款软件或删除本地已购桌宠资源后，账号仍拥有购买权益。

## 4. 需求 B：词库多选与导入体验

“词库”在当前代码中称为“互动词包”。用户已确认本轮同时包含以下两项：批量导入、多套同时启用。文件多选在桌面端已有基础，同时启用需要新增实现。

### 4.1 一次导入多个文件

- 保留 Windows / macOS 已有的多文件选择能力，统一入口提示“可多选 JSON/TXT”；Windows 当前按钮已标注可多选。
- 导入前显示本次选中数量、现有数量及剩余容量；数量上限暂沿用 5 套，是否提高另行确认。
- 批量检查格式、空内容、不可读取文件和重复项，再展示结果；单个文件失败应能定位原因，不把整批笼统显示为失败。现有桌面实现为整批校验成功后加入，以下预检流程是拟议优化。
- 建议采用“预检后确认有效项”的流程：先列出可导入和失败项，再一次确认导入有效内容；超出容量时让用户明确选择保留项，不静默截取前几个。
- 同名不同内容不能无提示覆盖，重复内容应提示跳过或明确替换；取消不改变原有配置。
- 导入内容解析后保存在应用管理的本地数据中；原文件移动后仍能使用。导入成功后刷新列表，失败重试不产生多份重复记录。
- 建议统一单文件最多 256 KiB、每动作最多 50 句、每句最多 60 字的校验与提示，处理去重；这是基于现有 macOS 边界的建议，Windows 当前需要补齐文件大小检查。
- Android 若纳入本轮同等体验，需新增文件多选和本地导入流程；仅改 Flutter 下拉框不能完成该能力。

### 4.2 同时勾选多个词包使用（已确认需要）

多套同时启用是本轮明确目标；具体默认行为建议如下：

1. 将单选词包改为勾选列表，能看到已启用数量；导入列表与启用列表分别保存。
2. 旧版已选词包迁移为仅勾选该词包，已有用户升级后行为稳定。
3. 新导入的词包提供“勾选本次全部”的便捷操作，建议默认保留已有启用集合，不再自动切换成最后导入的一套。
4. 建议每次先在已启用且有适用台词的词包中等概率选择，再在该包内取词；防止大词包完全压过小词包。相同动作下的重复句统一处理，并避免连续显示同句。具体混用权重待确认。
5. 删除已启用词包后同步移除选择；全不选时使用现有默认台词，并清楚标注。
6. 不同事件类型沿用原有词包字段与触发语义，不把仅适用于某类事件的句子混入其他事件。
7. 本地词包多选只作用于本地台词。现有内容互动 / 答题实时联网取题规则继续独立，见 [实时取题行为](2026-10-27-realtime-content.md)。

### 4.3 验收要点

- 单文件、多文件、超量、混合有效 / 无效、同名、重复、取消和重新导入均有明确结果。
- 现有配置可迁移，选择重启后保留，删除原始导入文件不影响已保存词包。
- 验证多套同时启用的选中集合正确生效、跨包取词、重复句处理、删除处理和空选择回退。
- “桌宠 GIF 也能批量导入”单列待确认，避免与词包多选混为一项已确定的要求。

## 5. 需求 C：在线桌宠市场、限量预览与付款下载

### 5.1 商品与入口

新增“桌宠市场”入口，提供商品列表、详情、预览、购买和“我的已购”。每个商品至少有稳定商品 ID、标题、介绍、封面、价格、支持平台、内容版本、资源数量与上架状态。

用户已确认按“角色包”售卖：一个商品对应同一个角色，包含 25+ 动作或表情素材；不是付款一次获得 25 个不同角色，也不是按每个动作分别收费。商品详情显示角色、所含素材数量和可预览样例。

| 档位 | 已确认价格 | 内容单位 |
| --- | --- | --- |
| 免费款（2026-10-29 补充） | 0 元，正式激活后领取 | 后台配置内容，可指定一个默认款 |
| 普通款 | 2.80 元 / 角色包 | 同一角色的 25+ 动作或表情素材 |
| 复杂或热门款 | 5.80 元 / 角色包 | 同一角色的 25+ 动作或表情素材 |

后台为每个商品设置免费或收费。收费时指定 2.80 / 5.80 元档位，金额以整数分保存为 280 或 580，固定在下单快照中；不会为了自动对账把金额改成 2.81 元等随机尾数。免费领取不创建付款订单或短码，但同样要求正式激活。后台可指定一个免费且已上架的默认款；默认款不自动覆盖用户当前桌宠。首版按一次取得该角色包指定版本的权益设计，后续更新是否包含在原价中另行确定。

市场下载内容存放在单独的市场图鉴区域，不直接占用当前最多 3 个本地自定义 GIF 的容量。2026-10-29 用户明确：只有正式激活用户可购买和使用市场桌宠，免费款也需激活后领取、下载和使用；未激活与试用用户仅可浏览和有限预览。此规则不改写原内置桌宠的试用体验。

### 5.2 可预览范围

用户要求保留两种后台配置：管理员手选可预览内容，或按排序取前五个。

- 已确认按“每个资源包”配置预览集合；资源包之间分别计算，不是整个市场共用五个名额。
- 建议明确区分“手动指定”“按排序前 N 个”“关闭预览”；N 默认 5。建议手动模式的空集合表示无预览，不自动切换为前五个。
- “前五个”依据后台保存的稳定展示顺序，并排除下架或无效内容；不足五个时展示现有数量。
- 商品可展示封面、介绍和内容数量；未授权预览的动画 / 动作只显示未开放状态或占位。
- 点击允许的预览可播放动图；建议在商品详情中预览，不自动把试看内容加入用户当前桌宠。
- 后台限制必须由服务端执行，不能先把完整资源传到客户端再仅隐藏入口。付费原文件不出现在公开目录响应中。
- 公开预览素材与付费完整包分开存储和发放。预览已经展示的像素内容可以被保存；本功能保护完整付费资源的获取权限，不承诺预览无法复制。

### 5.3 购买到使用流程

1. 用户选择角色包与付款方式并点击“下单”，服务端从已认证的设备身份取得账号，创建订单与简短付款备注码。创建成功后才展示付款面板：收款码方式展示二维码，好友转账方式展示转账说明，创建失败不展示无订单可关联的付款入口。
2. 订单固定账号、角色包 / 资源版本、金额、币种、收款账户、收款码配置版本和有效期；有效期从服务端创建时间起为 15 分钟，后续改价不修改已有订单金额。
3. 付款窗口集中展示角色包名称、2.80 / 5.80 元、醒目的五位短码、对应付款方式的收款码或转账说明，以及 15:00 倒计时；短码可复制，明确提示在付款备注或转账说明填写完整 `123AB`，不区分大小写（示例）。本地调试原型金额固定为 0.01 元。同账号同商品重复点击应复用尚未过期的待支付订单；已购商品直接显示下载 / 使用入口。
4. 收款码方式由用户手机扫码，在付款备注入口填写短码后确认支付；好友转账方式在向当前收款方发起转账时，将转账说明直接填写为五位短码。普通静态收款码不能自动带入桌搭子的订单码，电脑“复制”也不能假定会同步到手机；短码用于减少手工输入。付款后是否还能补备注不可依赖，操作引导必须放在付款确认之前。
5. wxlocal 读取官方收款通知或个人转账卡片，桥接按来源分别建立基线、解析并提交事件。当前真实样本已确认能提取备注、金额和稳定交易标识；其他模板、缺失字段或异常来源继续保留待核对。
6. 当前本地规则分为两条：个人转账仅在 `personal_transfer / incoming / observed / verified:false` 且短码、金额、币种、收款账户、稳定交易标识、来源消息时间、观察时间与首次接收时间均匹配有效订单时自动标记 `paid`；收款码仍在人工核实后确认。个人转账正常流程不要求领取或人工确认，客户端不能自行标记订单成功。
7. 在可重试、幂等的发放流程中为该账号生成购买权益。相同支付通知重试不会重复发放，单个交易号不能支付两个订单。
8. 客户端查询订单状态或收到通知，显示“订单已确认，可以下载测试资源包”；停止支付倒计时，关闭付款面板并进入下载状态。用户点击下载，不静默下载或安装。客户端按钮“我已付款”若后续新增，只触发重新查询，不能自行标记到账。正式资源市场的“使用此桌宠”入口仍属后续范围。
9. 用户可直接下载；建议通过服务端权限检查取得短期下载凭证，完整校验并保存资源后显示“使用此桌宠”。是否自动下载建议由用户选择。
10. 15 分钟内未支付，订单按超时规则关闭付款窗口，详情见 5.3.1。下载失败、关闭应用或重装后，已购买内容仍可从“我的已购”重新下载，不要求再次付款。

#### 5.3.1 十五分钟未支付与窗口关闭

- 服务端保存 `expiresAt = createdAt + 15 分钟`，超时任务与订单查询共同确保到期状态被处理；客户端只展示剩余时间，修改本机时间、重开窗口或重启客户端不能延长订单有效期。
- 到期时将仍待支付的订单标记为“已取消（超时）”，关闭的是付款弹窗，不是整个桌搭子程序；保留可查询的订单历史，在商品页提示重新下单。
- 客户端暂停、断网或系统休眠跨过截止时间，恢复时先移除过期付款入口，再同步订单结果，不能继续显示旧收款窗口让用户支付。
- 已被服务端确认付款的订单不得被超时任务取消。支付确认与到期处理需原子检查状态；到账处理失败不能丢失已付款事实。
- 用户提前关闭付款窗口，建议只隐藏窗口，原订单仍按原截止时间等待；重新打开显示原短码与剩余时间。明确点击“取消订单”才提前关闭订单。
- 静态收款码不会随窗口关闭而失效，用户保存截图后仍可能付款。过期订单、短码和付款记录必须保留，超时不能删除对账依据。
- 实际支付时间在有效期内、但通知迟到：只有在支付时间与交易可核实的情况下才补确认原订单并发放，客户端从“我的已购”取得结果，不重开旧收款窗口。
- 到期后才付款、付款时间不可核实或超时与到账存在争议：进入待核对，关联原订单人工补发或处理退款；不误归到新订单。wxlocal 的消息创建时间 / 本地捕获时间不能直接当作微信实际支付时间。
- 本地个人转账自动规则使用来源消息时间、观察时间及首次接收时间，三者都必须处于订单创建至截止区间，不能把这些时间宣传成已验证的结算时间。对于已在有效期内接收的旧候选，原样事件重送可按严格规则恢复过期订单；首次接收已超时、手动取消或字段不匹配的订单不自动放行，也不改写原时间。

### 5.4 唯一标识与付款备注

需要三个不同标识：

| 标识 | 用途 |
| --- | --- |
| `productId` / `petId` | 稳定标识售卖商品或其中的桌宠，不随购买者变化 |
| `orderId` | 标识一次订单，保存账号、商品、价格和状态快照 |
| `paymentReference` | 填入付款备注的五位码，固定三个数字加两个英文字母，由服务端关联收款账户并解析到对应订单 |

用户已确认固定五位：前三位是数字，后两位是英文字母，例如 `123AB`，不区分大小写；不带连字符或账号信息，不要求用户填写完整订单编号。后台用短码查到不可变的订单，再取得账号与角色包；不需要让短码本身携带可解密的长内容。

短码与完整订单 ID 分离，规则如下：

- 格式为 `[0-9]{3}[A-Z]{2}`，数字范围 `000` 至 `999`，字母范围 `AA` 至 `ZZ`，共 `1000 × 26 × 26 = 676000` 种组合。使用安全随机源分配并由数据库唯一约束兜底，不使用时间戳截断或可预测递增值。始终按字符串保存和显示全部五位，保留前导零。
- 同一收款账户内，一个短码只关联一个历史订单。订单取消、过期或付款后都不回收短码，避免旧截图迟到付款串到新订单。
- 676000 个组合耗尽后明确返回码池耗尽错误并停止新建订单；不擅自扩长、不复用历史码。容量调整必须作为另行确认的规则变更。
- 备注匹配时去除明确的首尾空格并统一字母大小写，`123ab` 与 `123AB` 匹配同一订单。其余内容必须符合完整五位格式；不从含糊长备注中任取片段，不模糊匹配相近字符，也不只凭 2.80 / 5.80 元金额猜订单。
- 输入错码且恰好指向另一笔同价订单时，静态收款码通常不能独立证明付款人与桌搭子账号归属。界面须醒目展示短码、提示付款前核对；异常申诉保留人工核账路径，不宣称短码可彻底消除误填。
- 短码仅作对账引用，不作登录、订单详情查询或下载授权。客户端仍需原账号凭据，支付事件也须来自受信桥接来源。

676000 种组合并不代表短码不可猜中或“不可破解”。订单访问、到账确认和资源下载依靠独立鉴权及服务端权益校验；知道短码不能查询他人订单、伪造到账或获得下载权限。本地原型分别使用客户端、通知桥接与管理员令牌，普通客户端不能自行标记已付款。

备注码属于某次订单，不是所有人购买同一桌宠都共用的商品码。持有码只能协助匹配到账，不能证明已付款，也不是下载权限。客户端不得自选账号 ID 来领取他人的购买内容。

#### 5.5.2 本地连接方式与后续扩展

收款机上的 wxlocal 接收指定微信支付通知 → 桌搭子收款适配器提取候选到账信息并写入持久发送队列 → 认证推送到桌搭子服务端 → 核对短码、金额、收款来源与交易 → 原子记录订单 / 发放权益 → 客户端更新下载入口。

适配器只发送本业务需要的收款字段，不推送普通聊天。桥接配置绑定指定收款微信账号，并与订单中的收款账户对应。`event_key` 用于通知重试幂等；交易编号另设去重约束，不能用消息本地 ID 冒充交易号。wxlocal 的回调成功只表示业务处理成功返回，不能被当作服务端已经发放权益。

本地通知捕获、待发送任务先持久化，HTTP 超时可带同一幂等键重试；服务器已成功但响应丢失时，不重复发放。新增监听从当前消息基线开始，首次启动前的历史不自动回放；重启恢复要求复用原消息库。需单独设计首次切换期间的核账，以及失败任务重排，不能假设 SDK 会无限自动补报。

#### 5.5.3 正式市场上线前需验证

本地好友转账已由用户选择“转出即成功”的业务规则，不能把这种放行策略表述为已独立核实微信结算。正式市场上线仍需明确采用的付款方式及以下条件；收款码的独立到账判断与好友转账消息匹配分开验收：

| 必须核实 | 影响 |
| --- | --- |
| 收款码确认最终到账；好友转账按已选业务规则严格识别结构化转账，不能接受付款截图或普通聊天文本 | 分别确定各支付方式的放行条件，不混淆转账消息与结算状态 |
| 能稳定取得实际金额、币种、收款账户归属和可靠付款时间 | 用于核对订单；缺乏可靠付款时间的迟到消息进入人工核对 |
| 当前收款码在付款前支持备注，且收款侧通知包含完整五位短码 | 决定本方案是否成立；聊天转账备注不能替代这项验证 |
| 能取得唯一交易号，或可验证的等价收款记录标识 | 用于交易去重，避免一笔付款多次或跨订单发货 |
| 机器人离线、重启后能补收 / 对账，接口支持重试 | 防止用户已付款但通知丢失 |
| 到账事件能来自受信来源，机器人到桌搭子接口可认证和防重放 | 避免伪造通知改变订单状态 |

当前本地个人转账已按上述业务规则实现自动匹配与权益发放，不能再将领取或人工确认作为正常路径前提。正式市场仍需完成表中上线验证；收款码保持人工核账，其他模板或缺少关键字段的异常事件保留待核对，不凭截图或金额猜单。后续若扩展收款码自动化，可另行评估商户接口验签回调与主动查单。所有人工处理都须保留交易依据和操作记录。

### 5.6 异常、权益与下载规则

- 付款备注缺失、错误、金额不符、过期付款或重复付款进入“待核对”，不静默丢弃付款记录。有效期内付款但消息迟到的情况按 5.3.1 核验，后台可核账、补发或登记退款。
- 订单状态建议包含待支付、待核对、已支付、已取消（手动 / 超时）、退款处理中、已退款；权益发放另有待发放 / 已发放 / 失败重试状态。到账成功但发放中断时应能恢复。
- 商品变价、下架、资源版本变更不改写已有订单。已购用户可下载的版本范围、下架后的继续下载和退款规则在收款前确定；建议首版保留已购版本下载。
- 购买权益按稳定账号保存；下载安装情况按设备保存。卸载整款软件或删除资源不删除权益；软件安装状态与资源安装状态分开显示。
- 2026-10-29 已确认：正式激活账号才能付费购买、免费领取、下载及使用市场桌宠；试用用户仅可浏览预览，不将有效试用授权当作正式激活。
- Android 重装后设备身份会变化。必须走账号恢复 / 绑定流程找回已购，不能仅靠旧安装 ID；设备额度问题不通过伪造新购买解决。
- 购买桌宠与基础软件激活分别记账。已确认必须先激活软件才能使用已购桌宠；购买不自动激活软件、延长试用或增加设备额度。
- 完整包放在受保护的存储位置，不复用现有公开资源包 URL。下载需验证账号权益，并限制凭证作用的商品、版本和有效期。
- 下载包校验清单、大小、SHA-256 及清单签名；解压限制路径、文件类型和总体积，只接受约定的资源与配置。下载不完整时不得覆盖已有可用版本。
- 完整资源已合法下载到设备后，不承诺能通过远程退款收回所有本地副本；退款后的重新下载 / 使用策略需明确。

### 5.7 后台管理与验收

后台至少支持：角色包上传与版本管理、草稿 / 上架 / 下架、免费 / 收费开关、唯一免费默认款、2.80 / 5.80 元档位、排序、预览模式、手选预览内容、收款码与收款账户配置、按完整订单号 / 五位短码搜索、15 分钟到期时间与取消原因、到账核对、购买权益、补发记录、下载状态及退款记录。各项实际实现进度见[2026-10-29 本地市场实现记录](2026-10-29-pet-market-implementation.md)，不把规划列表当作已验收结果。

验收覆盖：

- 手动预览集合、前五个、不足五个、关闭预览、下架内容，以及绕过界面请求未授权完整资源。
- 正常付款、重复通知、伪造通知、错备注、错金额、迟到到账、机器人离线补报与人工核账。
- 从点击下单到生成短码再展示收款码；固定三个数字加两个字母、大小写无关、前导零保留、并发分配、不复用旧码；676000 组合耗尽时明确报错而非扩位；同商品待支付订单复用。
- 普通款 280 分与复杂 / 热门款 580 分准确匹配，商品包内容为同一角色的 25+ 动作 / 表情，前五个预览按包计算。
- 15 分钟超时取消并关闭付款窗口；本机时间修改、休眠、断网和重开窗口均不续期；付款成功与超时同时发生不误取消。
- 有效期内付款但通知迟到、订单取消后扫码付款、缺少真实交易时间和误填另一有效短码等情况可追查，不凭金额猜订单。
- 实际收款码的付款前备注入口，以及收款侧通知短码 / 交易号 / 收款时间字段验证；仅测试聊天转账不算通过。
- 同一交易号只处理一次，不可跨订单重复使用；账号不能领取别人的权益。
- 已付款发放失败后恢复，重复点击购买不会重复扣款或生成多份有效权益。
- 下载中断、校验失败、重试、旧资源保留、重装恢复、同账号允许设备重新下载。
- 付款前准确展示平台兼容性、基础软件授权要求、资源容量限制与可下载范围。

## 6. 联合实施安排建议

三项一起规划和验收，代码实现时按依赖拆分；本文暂不指定版本号或发布日期。
